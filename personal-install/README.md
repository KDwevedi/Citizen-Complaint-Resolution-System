# personal-install — DIGIT/PGR you can stand up in a fresh dir

A self-contained workspace that brings up a full DIGIT stack on your laptop, mirrors what naipepea actually runs (same images, same auth pattern), seeds tenants + boundaries, and hands you off to the configurator's onboarding wizard for everything else. Goal: from a fresh `git clone` to a working citizen-complaint flow in ~10 minutes (mostly waiting for image pulls + JVM startup under Rosetta).

## Layout

```
personal-install/
├── config.env                   Single source of truth — port prefix, seed mode, tenant taxonomy, creds
├── stack/                       → symlink to ../ccrs-nairobi/local-setup
│   ├── docker-compose.deploy.yaml      ← upstream (CCRS local-setup, untouched)
│   ├── docker-compose.local.yaml       ← auto-generated by gen-compose.py (port-shift)
│   ├── docker-compose.naipepea.yaml    ← image overrides → naipepea registry
│   ├── docker-compose.extra.yaml       ← personal-install additions (configurator service)
│   ├── configurator-nginx.conf         ← nginx vhost mounted into the configurator container
│   └── (kong/, nginx/, configs/, db/, seeds/, gatus/, jupyter/, … from upstream)
├── data/                        → symlink to ../ccrs-nairobi-ansible/ansible/nairobi-mdms
│   ├── boundaries.json                 ← Nairobi: 1 county, 2 sub-counties, 9 wards
│   ├── employees.json                  ← 28 NCCG employee records (Phase 4 reference)
│   ├── mdms/                           ← 34 JSON files across 12 schema modules
│   ├── README.md, v2.11-user-service-upgrade.md   (Chakshu's notes; not consumed)
├── ansible/
│   ├── inventory.yml            Localhost target, vars driven by config.env env-vars
│   ├── playbook.yml             Pre_tasks (Kong wait + login) → seeds → ui-tasks → URLs banner
│   └── tasks/
│       ├── 02-seed-tenants.yml           ✓ creates root + city tenants in MDMS
│       ├── 03-seed-boundaries.yml        ✓ County → SubCounty → Ward + hierarchy + relationships
│       ├── 04-seed-mdms.yml              ◯ stub (configurator wizard handles this)
│       ├── 05-seed-employees.yml         ◯ stub (configurator wizard handles this)
│       ├── 06-seed-pgr.yml               ◯ stub (covered by MDMS seed)
│       ├── 07-seed-admin.yml             ◯ stub (configurator wizard creates admin in Phase 4)
│       ├── 08-start-digit-ui-esbuild.yml ✓ spawns host-side esbuild HMR for /digit-ui/
│       ├── 09-ensure-configurator.yml    ✓ builds dist + probes configurator container
│       └── 10-create-pgr-mvs.yml         ✓ applies pgr_mv_* DDL + initial refresh
├── sql/
│   └── pgr-mv.sql               Materialized-view DDL for the PGR dashboard (extracted via pg_dump from naipepea)
├── scripts/
│   ├── up.sh                    docker compose up + ansible (mode driven by config.env)
│   ├── down.sh                  docker compose down (-v for volume reset)
│   └── gen-compose.py           Port-shift upstream compose → docker-compose.local.yaml
└── .dev-logs/                   Generated — esbuild log, ansible run logs
```

**Important about the `stack/` symlink**: it points at the cloned upstream's `local-setup/` directory. The four files we own (`docker-compose.local.yaml`, `docker-compose.naipepea.yaml`, `docker-compose.extra.yaml`, `configurator-nginx.conf`) live *inside* that symlinked directory — they were written there by `gen-compose.py` and the setup. Don't be confused if a `git status` in the cloned upstream shows them as untracked; they're personal-install artifacts.

## Prerequisites

Common to every host:

| Tool | Why |
|---|---|
| **Docker ≥ 24** with **≥ 12 GB RAM, ≥ 20 GB disk** | 28-service stack + Rosetta-emulated JVMs eat memory. Default 8 GB will OOM under Rosetta. |
| **`python3` + `git` + `rsync` + `curl` + `lsof`** | Standard CLI deps. |
| **`ansible-playbook`** | `up.sh` auto-installs via `pip3 install --user ansible` if missing. |
| **`node ≥ 20` + `npm`** | For the configurator's vite build (and host-side esbuild if you opt-in). |

OS-specific:

| Host | Setup | Behavior |
|---|---|---|
| **macOS (Apple Silicon, M1/M2/M3/M4)** | Docker Desktop with **Rosetta enabled** (Settings → General → "Use Rosetta for x86_64/amd64 emulation on Apple Silicon") | `up.sh` auto-detects arm64 macOS and exports `DOCKER_DEFAULT_PLATFORM=linux/amd64`. JVM services run ~2× slower than native amd64. |
| **macOS (Intel)** | Docker Desktop, no special config | Native amd64 — no emulation. |
| **Linux (x86_64)** | Docker Engine or Docker Desktop, no special config | Native amd64 — fastest stack startup. |
| **Linux (arm64, e.g. Graviton)** | Docker Engine + qemu-static for amd64 emulation: `docker run --rm --privileged multiarch/qemu-user-static --reset -p yes` | Same Rosetta-style emulation Apple Silicon uses; slower. |
| **Windows 10/11 + WSL2** | Docker Desktop with WSL2 backend; clone `personal-install` *inside* the WSL2 filesystem (`/home/<user>/...`, NOT `/mnt/c/...` — bind-mount perf is awful from `/mnt/c`) | `up.sh` detects WSL via `/proc/version` and uses Linux behavior |

`up.sh` auto-detects the host via `OS=auto` (default). Override explicitly in `config.env` if needed: `OS=macos`, `linux`, `wsl`, or `auto`.

## Two install modes

| Mode | Pick when | How |
|---|---|---|
| **Plain** — bare DIGIT stack, no opinionated tenant data | You want to drive everything (tenant, boundaries, depts, employees, theme) through the configurator's onboarding wizard interactively | Set `SEED_DEMO_DATA=false` in `config.env`, then `./scripts/up.sh`. Or one-shot: `SEED_DEMO_DATA=false ./scripts/up.sh`. Ansible runs but only spawns the UI processes + URLs banner — no MDMS / boundary writes. |
| **Nairobi-flavored** *(default)* | You want a pre-populated demo: `ke` + `ke.nairobi` tenants and 12 boundaries (Nairobi City: 2 sub-counties, 9 wards) ready for the wizard's Phase 4 jurisdiction picker | `SEED_DEMO_DATA=true` (default) — `./scripts/up.sh`. |
| **Stack-only escape hatch** | You want zero ansible — just bring up the docker compose and use the configurator end-to-end | `./scripts/up.sh stack` (no ansible at all; the host-side esbuild + configurator-build tasks won't run, so digit-ui will only be the docker container, not HMR) |

**All three modes** end the same way: open `http://localhost:16172/configurator/`, log in as `ADMIN / eGov@123` on tenant `pg`, run the onboarding wizard. The wizard's Phase 1 creates tenants — same MDMS write that ansible's `02-seed-tenants.yml` does, just clicked instead of scripted. Plain mode does Phase 1 yourself; Nairobi mode skips it.

## Usage

```bash
cd personal-install
./scripts/up.sh             # full: pull + compose up + ansible (driven by config.env)
./scripts/up.sh stack       # docker-compose only (no ansible at all)
./scripts/up.sh seed        # ansible only (assumes stack already up)
./scripts/down.sh           # tear down (volumes preserved)
./scripts/down.sh -v        # tear down + drop volumes (full reset)

# One-shot env overrides without editing config.env:
SEED_DEMO_DATA=false ./scripts/up.sh           # plain install
PORT_PREFIX=26 ./scripts/up.sh                 # different port range
PERSONAL_TENANT_ROOT=in PERSONAL_TENANT_CITY=in.mumbai ./scripts/up.sh   # different tenant
```

Re-running `up.sh` is cheap and idempotent — every step (tenant create, boundary create, npm install, dist build, esbuild spawn) checks before doing.

## What ansible does vs what the configurator does

| Step | Done by | Why |
|---|---|---|
| Docker stack (28 services) | `up.sh` (compose) | No SPA can `docker compose up` |
| Tenant header in MDMS (`ke`, `ke.nairobi`) | ansible `02-seed-tenants.yml` | Required before configurator's onboarding wizard can target the tenant |
| Boundaries (County → SubCounty → Ward + hierarchy + relationships) | ansible `03-seed-boundaries.yml` | Wizard's Phase 4 (Employees) needs boundaries pre-seeded for jurisdiction picking |
| PGR dashboard materialized views | ansible `10-create-pgr-mvs.yml` | pgr-services has a `DashboardRefreshScheduler` that *refreshes* MVs every minute but doesn't *create* them. naipepea has them from a hand-applied DDL. We capture that DDL via `pg_dump` and apply it on a fresh stack so `/manage/pgr-dashboard` works. |
| digit-configurator dist build + container reachable | ansible `09-ensure-configurator.yml` | Builds dist via vite if missing, probes container; the docker service mounts the dist read-only |
| digit-ui-esbuild HMR (host-side process) | ansible `08-start-digit-ui-esbuild.yml` | esbuild's proxy hardcodes `127.0.0.1` so the dev server can't run inside docker; we spawn it on the host |
| Roles, departments, designations | **Configurator wizard, Phase 2** | Heavily UX-driven; PRs #1–#42 polished it |
| Complaint types (PGR ServiceDefs) | **Configurator wizard, Phase 3** | Same |
| Employees + ADMIN on city tenant | **Configurator wizard, Phase 4** | Bulk-import XLSX, role assignment, jurisdiction picker |
| Theme + branding | **Configurator wizard, Phase 5** | The new v3 designer-1:1 form (PR #42) is here |

After ansible finishes, the playbook's last task prints all URLs. Open the configurator, log in, run the wizard targeting `ke.nairobi`, follow the on-screen prompts. The wizard surfaces the real `digit-ui` employee URL on its Complete page.

## How seeding works

Seed data flows from a symlink chain:

```
egov/personal-install/data/                                        (symlink)
  ↓
egov/ccrs-nairobi-ansible/ansible/nairobi-mdms/                    (sparse-cloned)
  ↓
ChakshuGautam/Citizen-Complaint-Resolution-System @ nairobi branch (commit 0d43bf264, 2026-04-29)
```

Per file:

| File | Used by | What's inside |
|---|---|---|
| `data/boundaries.json` | `03-seed-boundaries.yml` (var `seed_boundaries_file`) | `{ county: "Nairobi City", subCounties: { Makadara: [4 wards], Kibra: [5 wards] } }` |
| `data/employees.json` | `05-seed-employees.yml` *(stub)* | 28 records: `{name, department, designation, mobileNumber, email?, roles?, wards?}` |
| `data/mdms/<module>/<schema>.json` | `04-seed-mdms.yml` *(stub)* | Array of `{tenantId, data: {...}}` per schema. 34 files across 12 modules. |

What's **NOT** sourced from `data/`: tenant headers (constructed inline from env vars), bootstrap admin (env-only).

To swap in your own data:

```bash
# point seed_boundaries_file at your own file
ansible-playbook ... -e seed_boundaries_file=$PWD/path/to/your-boundaries.json

# OR just drop a new boundaries.json into data/ — it's a writable symlink
cp my-boundaries.json data/boundaries.json
./scripts/up.sh seed
```

## Adding more tenants

Want a second tenant alongside `ke.nairobi`? Two options:

**Option 1 — re-run ansible with different env-vars.** Edit `config.env`:

```bash
PERSONAL_TENANT_ROOT=in
PERSONAL_TENANT_CITY=in.mumbai
```

…then `./scripts/up.sh seed`. The previous `ke.nairobi` records stay (idempotent — only missing things get created). One-shot:

```bash
PERSONAL_TENANT_ROOT=in PERSONAL_TENANT_CITY=in.mumbai ./scripts/up.sh seed
```

**Option 2 — use the configurator's onboarding wizard, Phase 1.** No standalone `/manage/tenants/create` route exists yet (per `TESTING-STEPS.md` §10) — Phase 1 of the wizard is where tenant creation lives. Effect is identical to ansible's `02-seed-tenants.yml`; just clicked.

If you want different boundary data for a second tenant, drop a new `boundaries.json` into `data/` and pass `-e seed_boundaries_file=$PWD/data/<other-county>.json`.

## Adding more services to the stack

The pattern: append to `docker-compose.extra.yaml`. The configurator service was added this way:

```yaml
# docker-compose.extra.yaml
services:
  my-new-service:
    image: ${REGISTRY_URL}/...:tag    # match naipepea registry pattern
    container_name: my-new-service
    ports:
      - "${PORT_PREFIX:-16}NNN:80"
    networks:
      - egov-network
    depends_on:
      kong: { condition: service_healthy }
```

Then `./scripts/up.sh stack` to bring it up. The compose merge resolves `egov-network` against the network defined in `docker-compose.local.yaml`.

## Image reconciliation — why we mirror naipepea's registry

The CCRS `local-setup/docker-compose.deploy.yaml` references `egovio/*` Docker Hub tags last touched ~4 months ago. naipepea was hand-rebuilt to use a private registry of continuously-updated images. Locally we layer `docker-compose.naipepea.yaml` to override every service's `image:` to the same tag naipepea runs. Set `REGISTRY_URL=<your-host>` in `config.env` to point at your own mirror.

```
local upstream:    egovio/pgr-services:multiarch-d448cb7         (4 months old, no /v2/dashboard)
naipepea-mirror:   ${REGISTRY_URL}/pgr-services-dev:inbox-filters
                   (sha 224773a276e5 — same SHA naipepea is running)
```

The registry is anonymously pullable — no docker login needed.

**Tag-pinning gotcha**: `:latest` in the registry has been overwritten with newer builds since naipepea pulled. `:latest` from Docker Hub today is *not* what naipepea is running. We pin pgr-services to `:inbox-filters` instead — that's the named tag of the SHA naipepea actually has on disk.

3 services don't fully reconcile and stay on public images — comments in `docker-compose.naipepea.yaml` document why:

| Service | Reason |
|---|---|
| `telemetry` | Upstream-only; not on naipepea |
| `egov-workflow-v2` | naipepea uses a locally-built `:sla-reset` tag (not in registry). For full parity: `ssh naipepea 'docker save egov-workflow-v2:sla-reset' \| docker load`. |
| `jupyter` | Built locally from a Dockerfile; naipepea has `tilt-demo-jupyter:latest` |

To regenerate the override file when naipepea drifts: re-grep naipepea's compose (`ssh naipepea 'grep image: /opt/digit/docker-compose.egov-digit.yaml'`) and update `docker-compose.naipepea.yaml` (manual; could be scripted later).

## Configuration knobs (config.env)

| Var | Default | Purpose |
|---|---|---|
| `OS` | `auto` | Host OS / arch. `auto` = detect via `uname` + `/proc/version` (works for everyone). Explicit values: `macos`, `linux`, `wsl`. Drives whether `up.sh` exports `DOCKER_DEFAULT_PLATFORM=linux/amd64` for Rosetta-style emulation. |
| `PORT_PREFIX` | `16` | Two-digit prefix for host ports. `16` avoids collision with the naipepea SSH tunnel (18) and `dev.sh` esbuild (18080). Bump to `17` or `26` for additional stacks. |
| `SEED_DEMO_DATA` | `true` | `true` = ansible seeds tenants + boundaries (Nairobi-flavored). `false` = plain install, drive everything via the configurator wizard. |
| `PERSONAL_TENANT_ROOT` | `ke` | Root tenant code seeded into MDMS when `SEED_DEMO_DATA=true`. Ignored when `false`. |
| `PERSONAL_TENANT_CITY` | `ke.nairobi` | City tenant code seeded when `SEED_DEMO_DATA=true`. |
| `BOOTSTRAP_TENANT` | `pg` | The CCRS-default bootstrap tenant where ADMIN exists |
| `BOOTSTRAP_USER` | `ADMIN` | Superuser login |
| `BOOTSTRAP_PASSWORD` | `eGov@123` | Superuser password |
| `DOCKER_DEFAULT_PLATFORM` | derived from `OS` | Set automatically by `up.sh` on macOS arm64 / non-amd64 Linux. Override only if you know what you're doing. |

Ansible-only flags (not in `config.env`; pass via `-e`):

| Var | Default | Purpose |
|---|---|---|
| `start_esbuild` | `true` | Spawn host-side digit-ui-esbuild during `seed`. Set `false` to use only the docker `digit-ui` container. |
| `ensure_configurator` | `true` | Build configurator dist + probe container. Set `false` to skip. |
| `enable_stubs` | `false` | Run the unfinished MDMS / employees / PGR / pre-admin stubs. Use the configurator wizard instead. |

## Resource picture

The compose stack has 28 services.

| Resource | macOS arm64 (Rosetta) | Linux amd64 (native) |
|---|---|---|
| Disk (images + runtime data) | ~20 GB | ~18 GB |
| RAM (idle full stack) | 10–12 GB | 6–8 GB |
| RAM (under load) | 14–16 GB | 9–10 GB |
| Boot — first run (cold pull + cold JVMs) | ~60 min (mostly registry pull) | ~15 min |
| Boot — subsequent (images cached, volumes preserved) | ~5 min | ~2 min |
| Boot — re-seed only (`up.sh seed`) | ~30 sec | ~10 sec |

**Verified end-to-end timing on a clean run** (M-series Mac, `down.sh -v` → `up.sh`):

```
docker compose pull (cache hits)              ~10 sec
docker compose up -d  (starts all 28)         ~2 min  (just the create-and-launch)
JVM cold-starts under Rosetta cascade         ~5–8 min  (egov-enc, egov-localization, egov-user, kong)
ansible playbook (44 tasks)                   ~30 sec
─────────────────────────────────────────────
Total: ~10–12 min from clean tear-down to all-green
```

The bottleneck is JVM cold-start under Rosetta. On native amd64 Linux, the same flow is ~3–5 min total because each JVM boots in seconds instead of ~2 min.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Pull fails: *"no matching manifest for linux/arm64/v8"* | naipepea images are amd64-only and Apple Silicon defaulted to arm64 | `up.sh` exports `DOCKER_DEFAULT_PLATFORM=linux/amd64` automatically when `OS=auto` detects macOS arm64. If invoking `docker pull` manually, pass `--platform linux/amd64`. |
| `docker compose up -d` halts with *"dependency egov-localization is unhealthy"* | JVM took longer than the compose healthcheck timeout (Rosetta is slow) | Wait 30s, then re-run `./scripts/up.sh stack`. JVMs warm up; compose's `up -d` is itself idempotent. |
| `digit-ui` container exits with *"host not found in upstream 'kong'"* | Race: nginx started before Kong DNS was up | `docker compose ... up -d --no-deps digit-ui`. The Kong DNS will be ready by the time you re-trigger. |
| Configurator at `:16172` blank or 404s on API calls | dist not built or wrong base path | `09-ensure-configurator.yml` builds it for you; if you bypassed ansible, run `cd ../digit-configurator && npx vite build --base=/configurator/` then re-run `up.sh seed`. |
| `/manage/pgr-dashboard` 400 → *"No static resource v2/dashboard"* | Wrong pgr-services image (public Docker Hub doesn't have the dashboard route) | Confirm `docker inspect pgr-services` shows `:inbox-filters`. If it shows `:latest`, your `gen-compose.py` ran but the override didn't apply — verify `up.sh` includes `-f docker-compose.naipepea.yaml`. |
| `/manage/pgr-dashboard` 400 → *"BadSqlGrammarException ... pgr_mv_kpi"* | Materialized views weren't seeded | Re-run `./scripts/up.sh seed --tags=pgr-mv`, or apply manually: `docker exec -i docker-postgres psql -U egov -d egov < sql/pgr-mv.sql` |
| `/manage/pgr-dashboard` 400 → *"materialized view ... has not been populated"* | MVs created but never refreshed | Wait 60s for `DashboardRefreshScheduler` to tick, or trigger manually: `docker exec docker-postgres psql -U egov -d egov -c "REFRESH MATERIALIZED VIEW pgr_mv_kpi; ..."` |
| digit-ui shows tenant `uitest` instead of `ke.nairobi` | wrong globalConfigs.js loaded | `08-start-digit-ui-esbuild.yml` writes `globalConfigs.personal-install.js`; check `.dev-logs/digit-ui-esbuild.log` for which file it loaded |
| `vendor-digit-ui-css.js` 500 errors during esbuild predev | unpkg flaky | Retry; or copy `public/vendor/*.css` from a working `digit-ui-esbuild` clone |
| Stack OOMs / containers killed | Docker Desktop RAM ≤ 8 GB | Settings → Resources → bump to ≥12 GB |
| Login from `ke.nairobi` returns *"Invalid login credentials"* | No ADMIN user on `ke.nairobi` yet | Use the configurator wizard (Phase 4) to create one. Pre-seed via `--tags=admin -e enable_stubs=true` collides with the wizard, so prefer the wizard. |
| WSL2: bind-mount perf is brutal | Cloned `personal-install` is on `/mnt/c/...` | Move it inside the WSL2 filesystem (`/home/<user>/...`); compose volume mounts are 10× faster. |

## Reset / tear down

```bash
./scripts/down.sh              # stop containers, keep volumes
./scripts/down.sh -v           # stop + drop all data (postgres/kafka/minio reset)
./scripts/up.sh                # bring back up after either; idempotent

rm -rf personal-install                            # full local cleanup (keep symlink targets)
rm -rf personal-install ccrs-nairobi-ansible       # also clears the seed-data source
```

The seed playbook is idempotent — re-running on a populated stack reports `0 changed` if nothing's missing.
