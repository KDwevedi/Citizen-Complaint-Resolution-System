# Decisions from the PR #36 line comments (2026-10-04)

These come from the owner's comments on the design and the sync-matrix gaps. They go into revision 7.

## Big simplifications

- **No sub-tenants going forward.** Every tenant is a plain id. Bindings, membership, citizen accounts and role tenants all use that id; any exception is handled by hand. This resolves GAP-17, GAP-24 and GAP-25.
- **One phone rule per deployment.** Cross-country numbers are not served. A phone change that fails the tenant's mobile rule is rejected up front (GAP-18).
- **`kcbff-` and `kcbffc-` were never in production.** Delete every `kcbff-` account, used or not (D13 / GAP-27). Nothing migrates or adopts old `kcbffc-` accounts; the rules only need to be right going forward (GAP-20, GAP-42).
- **Minimal disruption.** Keep old behaviour wherever possible. PGR's "file on behalf of a citizen" keeps its behaviour, except that it also finds BFF-created citizens by mobile (GAP-05).
- **egov-user fork tables are ignored.** Each box is checked for a stock image (GAP-32).

## Ownership and sync

- **Employee names are DIGIT-owned.** The admin sets them in HRMS, and the employee can edit them in their profile; Keycloak gets a copy. The founder's name is the exception: it comes from signup and is written into HRMS once (GAP-03).
- **Citizen name:** the phone number when nothing else is known, matching the legacy flow (to confirm). A phone-number name is not mirrored into Keycloak as a real name (GAP-04).
- **Name mapping:** Keycloak `firstName` = the full DIGIT name, `lastName` = empty and not required. Masked values are never copied (GAP-06).
- **Identity providers:** IMPORT mode only. Name and email are filled once at first sign-in and never overwritten; providers are a source for discovery, not the limit (GAP-07).
- **Email:**
  - staff email is changeable: self-service through Keycloak `UPDATE_EMAIL` (verify the new address, notify the old one), or by an admin when the old address is lost;
  - it reaches DIGIT only after verification;
  - configurator employee screens send email changes to the BFF/Keycloak, never to HRMS (GAP-01, GAP-36).
- **Employees need an email to be linked.** The admin supplies it; employees without one show "needs an email" (GAP-12).
- **Phone updates are allowed**, including for legacy citizens once the PGR lookup fix lands (GAP-19).
- **Tenant name = Organization name.** MDMS holds the tenant name, and the BFF mirrors it into the Keycloak Organization (GAP-30, to confirm in review).
- **Person locale is not synced in v1.** The tenant's languages come from onboarding (GAP-43).

## Lifecycle

- **One Keycloak password per person**, the same for every tenant and surface. Accepting an invite includes password setup for new people. The DIGIT-side derived credential is set only when a binding becomes active (GAP-13).
- **HRMS deactivation revokes**, on the same path as a role change (GAP-08).
- **"Remove member" in the configurator** = HRMS deactivate + BFF remove, as one action; founder replacement does the same (GAP-21).
- **Inactive staff** see the tenant with an "account inactive" message (GAP-22).
- **Disabling a tenant or Organization** revokes its members' tokens (GAP-29).
- **Invitation expiry:** a per-tenant MDMS setting the workspace owner edits in the configurator, between 1 hour and 90 days, defaulting to 14 days (GAP-38).
- **Mirror immediately** on link, accept and remove (GAP-39). Reconcile covers only HRMS-originated changes, on its interval.
- **Audit record** on Keycloak user deletion (GAP-37).

## Rollout safety

- **Feature flag** `IDENTITY_STAFF_CREDENTIAL_MODE=rotate|derived`, per box.
- **Snapshot** of `eg_user` and HRMS before the first rollout on each box (GAP-10).
- **One-time job:** convert old account links to bindings and add membership, run on every box before D10 is switched on (GAP-11).
- **Logout-once at binding activation:** the BFF logs out the person's existing native DIGIT token. Refresh tokens remain a documented limit, ≤ 14 days (GAP-14).

## Scope

- **Legacy native password paths** (direct egov-user calls, the legacy change and forgot password screens, HRMS's SMS'd password) are fine for now. They stay "tracked separately" and do **not** block D10 (GAP-15, GAP-16).
- **Open, to clarify later:** employees whose HRMS record sits at a city-level tenant aren't served by the new identity system for now (GAP-25 follow-up).
- **Leftover Keycloak groups and roles:** a one-time clean-up, plus a test that nothing reads them for authorization (GAP-31).
